# 后续内存方案

当前 `switch-final-runtime.json` 的 macOS release：主程序与常驻 Mihomo 合计 RSS 峰值 219.82 MB，距 150 MB 还差 69.82 MB。20 项功能检查通过，资源脚本因预算超限退出 2。上一轮为 217.12 MB；本次流程新增连续快切与失败保存，不能把全部差额归因于某一改动。physical footprint 约 115.61 MB 是另一指标，不能替代 RSS。

历史 `nav-delivery-memory.txt` 中有约 13.9 MiB CPU 画布、14.1 MiB CoreAnimation 存储、16 MiB 空闲但仍驻留的大块分配缓存。本次 `switch-final-memory.txt` 在关闭并重开窗口后显示约 27.9 MiB 活动大块分配、14.1 MiB CoreAnimation、约 2 MiB 空闲大块缓存。活动大块的尺寸接近两份画布，但仅凭尺寸不能断定引用来源或泄漏，需用分配栈确认。它们不能直接相加当作可节省量。内核约 44 MB；单靠清理几 MB 模型不足以达到目标。

| 顺序 | 方案 | 收益与代价 |
| --- | --- | --- |
| 1 | 在 Windows 实机跑相同资源流程 | Windows 没有 macOS 的 CoreAnimation 路径，不能套用 macOS 数字。先取得真正的目标平台基线，再决定优化点。现有交叉编译不能提供运行内存证据。 |
| 2 | 优先追踪窗口关闭、重开后的缓冲引用和大块分配栈 | 保持画质与动画。先确认两份画布大小的活动分配各由谁持有，再决定是否能释放或共享；不能把历史的 16 MiB 空闲缓存当作本次现成收益。此次波形路径改为预留字符串容量并直接写入，避免逐点创建临时字符串，但尚不能把它算作确定的 RSS 收益。 |
| 3 | 单独对比 Slint 的原生 GPU 渲染 | 当前 Slint 1.18.1 提供 `renderer-skia`、`renderer-femtovg-wgpu` 等功能，可研究 Metal / Direct3D。可能改变 CPU 画布与合成副本的开销，也可能增加纹理、驱动缓存和包体积。必须同时测 RSS、physical footprint 与 GPU 资源，不能只把内存移到 GPU 后宣布达标。 |
| 4 | 若主要目标是托盘驻留占用，将主界面独立为按需启动的进程 | 界面关闭时可真正释放渲染器和字体映射，Mihomo 继续工作。需要 IPC 与界面状态恢复，会增加打开界面的延迟；对界面展开时的峰值没有同样收益。当前关闭窗口已经释放 Slint 窗口组件，进程内库映射仍会保留。 |

不建议继续盲目降低 Go 内存限制：目前已经使用 `GOMEMLIMIT=16MiB`、`GOGC=50`，进一步压低可能增加回收开销和延迟。mimalloc 试验曾升至约 233 MB，已撤回；旧构建的 macOS 节省内存分配选项仅显示几 MB RSS 的差额，还需要在相同二进制上重复对照。

这些方案均未证明达到 150 MB。每项实验应使用新进程，保留完整分辨率、字体和动画，并运行真实入口的启动、并发流量、订阅更新、快速切换、六页访问、托盘关闭与重开流程。
